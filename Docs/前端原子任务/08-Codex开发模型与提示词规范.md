# Codex 开发模型与提示词规范

## 一、结论

本项目不使用单一模型和最高推理强度贯穿全部任务。统一采用以下分级，以控制返工率、响应时间和额度消耗：

1. 常规实现默认使用 `5.6 Terra`，推理强度选择高（`high`）。
2. 简单、边界清楚且低风险的修改使用 `5.6 Terra`，推理强度选择中等（`medium`）。
3. Unity 生命周期、异步竞态、原子切换、失败恢复、安全和性能问题使用 `5.6 Sol`，推理强度选择高（`high`）或超高（`xhigh`）。
4. 最高（`max`）和极致（`ultra`）只用于升级处理，不作为任何原子任务的初始配置。
5. `5.6 Luna` 不负责完整原子任务，只能辅助生成重复配置、测试数据、注释初稿和清单，结果必须由任务主模型复核。
6. `5.5` 不用于新任务。

> 重要：提示词不能替代 Codex 界面中的真实模型和推理强度选择。任务矩阵定义的是最低配置要求，不是唯一允许配置；提示词中的配置仅用于核对，不能让当前会话自行切换模型。

## 二、配置下限判定

模型与推理强度必须分别比较，不能用更高的其中一项补偿另一项不足。

| 配置维度 | 本项目比较顺序 | 判定说明 |
| --- | --- | --- |
| 模型能力 | `5.6 Luna` ＜ `5.6 Terra` ＜ `5.6 Sol` | `5.5`不属于新任务允许的等价配置；对要求 Terra 或 Sol 的任务一律视为低于要求 |
| 推理强度 | 低（`low`）＜中等（`medium`）＜高（`high`）＜超高（`xhigh`）＜最高（`max`）＜极致（`ultra`） | 只比较当前模型在 Codex 界面实际支持的等级 |

执行规则：

1. 当前模型不低于任务要求，且当前推理强度不低于任务要求：允许立即继续执行。
2. 当前模型或当前推理强度任一项低于任务要求：必须停止实施，明确指出不足项并提醒在界面中升级配置。
3. 当前模型或推理强度高于任务要求：无需降级，可继续执行；最终报告中记录任务最低要求和实际使用配置。
4. 任务要求 `5.6 Terra`＋高（`high`）时，`5.6 Sol`＋高、超高、最高或极致均可继续；`5.6 Sol`＋中等仍必须停止，因为推理强度低于要求。
5. 任务要求 `5.6 Sol`＋超高（`xhigh`）时，只有 `5.6 Sol`＋超高、最高或极致可继续；`5.6 Terra`＋极致仍必须停止，因为模型低于要求。

## 三、推理强度选择规则

| 推理强度 | 使用条件 | 本项目规则 |
| --- | --- | --- |
| 低（`low`） | 只读查询、单文件定位、无需设计判断 | 不用于正式实现任务 |
| 中等（`medium`） | 边界清楚、影响范围小、验收方式明确 | 仅用于任务-006、025、027及低风险辅助工作 |
| 高（`high`） | 需要追踪跨文件逻辑、检查边界条件并完成测试 | 常规开发默认值 |
| 超高（`xhigh`） | 跨运行时、异步竞态、资源生命周期、失败恢复或安全发布 | 复杂核心任务默认值 |
| 最高（`max`） | 已确认属于最困难问题，质量优先于耗时和额度 | 同一问题连续两次修复失败后使用 |
| 极致（`ultra`） | 问题可拆成多个独立方向，需要多个子代理并行交叉验证 | 仅复杂问题升级且适合并行分析时使用 |

升级规则：

1. 首次实现失败：保留当前模型和推理强度，先复现、缩小范围并补充诊断证据。
2. 同一问题连续两次修复失败：停止沿用原思路，切换为 `5.6 Sol`＋最高（`max`）。
3. 若问题能独立拆分为前端、Unity、协议、性能或测试等至少两个方向：切换为 `5.6 Sol`＋极致（`ultra`），创建多个子代理独立分析，汇总结论后再修改。
4. 未达到升级条件时不得直接使用最高或极致，避免用更多推理掩盖需求、数据或映射缺失。

## 五、通用开发提示词

发送前先在 Codex 界面按照“任务模型与推理强度矩阵”确认任务最低配置，然后复制以下提示词并替换方括号内容：

```text
请执行 F:\WorkSpace\WebDLPro\Docs\前端原子任务\[任务文档名称].md 中的任务-[任务编号]。

执行配置核对：
- 任务最低模型：[模型名称]
- 任务最低推理强度：[中文强度]（[配置值]）
- 当前模型和当前推理强度均不低于上述最低要求时，可以直接继续执行；实际配置高于最低要求时无需降级。
- 当前模型或当前推理强度任一项低于最低要求时，必须先停止并提醒我在界面中升级配置，不要直接开始修改。

开始前必须完整阅读：
1. F:\WorkSpace\WebDLPro\Docs\电力全流程平台-前端架构设计.md
2. F:\WorkSpace\WebDLPro\Docs\前端原子任务\00-任务总览.md
3. 当前任务所属文档。
4. 当前任务直接引用的通信、映射或拓扑规范。
5. 任务涉及的现有实现；已有功能和样式必须优先复用，禁止根据描述猜测。

执行要求：
1. 先检查需求合理性、前置任务、工作区未提交修改和阻塞资料，再开始实施。
2. 仅执行任务-[任务编号]，不得顺带实施后续任务或扩大职责范围。
3. 先给出简短实施计划和预计修改文件，再直接完成范围内修改。
4. 所有新增或修改代码必须使用 UTF-8 编码，并补充与代码一致的详细中文注释。
5. 优先保证性能和资源释放，避免重复查询、重复渲染、无限缓存、重复监听、计时器泄漏和 Unity 资源泄漏。

8. 若测试失败，先判断是否由本次修改导致；不得为通过测试而修改无关代码。
9. 最终按“变更结果、修改文件、验证结果、性能与释放、剩余风险”五项报告。

完成标准：
- 当前任务文档中的需求、交付和验收全部满足。
- 相关测试通过，或明确给出无法执行的客观原因和人工验证步骤。
- 没有遗留调试代码、重复监听、未释放资源和无上限缓存。
```

## 七、复杂问题升级提示词

仅在同一问题连续两次修复失败后使用。优先选择 `5.6 Sol`＋最高（`max`）；适合并行交叉验证时选择 `5.6 Sol`＋极致（`ultra`）。

```text
这是同一问题连续两次修复失败后的升级诊断任务。当前选择应为 5.6 Sol，推理强度为最高（max）；如果问题可拆成多个独立方向且当前账户支持，则改用极致（ultra）。

停止沿用前两次修复假设。先复现问题并整理两次失败证据，再从以下方向独立分析：
1. 前端状态、事件监听和异步竞态。
2. Unity 场景、桥接和资源生命周期。
3. 外层与内层通信协议、关联标识、会话隔离和回环阻断。
4. 测试覆盖、性能回归和发布环境差异。

适合并行时创建多个子代理，每个子代理只负责一个独立方向；等待全部结果后交叉验证，形成唯一根因假设和最小修复方案。没有证据前不得继续试错修改。

实施修复后必须新增回归测试，并报告根因、为什么前两次方案失败、修复范围、验证结果和仍存在的风险。
```
