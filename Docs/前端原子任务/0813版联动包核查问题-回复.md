## 一、共同部署前提

双方会议已经确定：平台服务和可视化服务分别独立部署，平台通过内嵌框架（`iframe`）加载我方可视化服务；不是把我方构建目录导入平台后，再由平台修改压缩脚本中的配置。

本文后续均以该模式为准：

```text
平台父页面
  └─ iframe → 我方可视化壳服务
                 └─ iframe → 我方 Unity 网页图形入口
```

平台负责父页面、设备绑定、运行时清单和设备状态；我方负责可视化壳、拓扑、Unity 入口和协议消费。双方通过跨窗口消息（`postMessage`）以及运行时清单接口协作。

平台反馈中“导入联动包后自动改写地址、Unity 路径、父源和最小尺寸”的同源托管方案不作为本项目正式部署方案。若后续需要改为平台托管，必须另行确认部署模式，不能与本回复混用。

## 二、问题一：基础清单缺少可绑定节点声明

### 2.1 我方确认

该问题属实，责任在 0813 基础清单和打包配置。0813 燃气总览共有 23 个节点，当前全部声明为：

```json
"doubleClickBehavior": "none"
```

因此平台按双方已确认的规则注入 0 台设备，无法触发设备双击事件、二维状态映射和三维状态同步。

### 2.2 修正口径

燃气场景中 23 个总览源节点全部需要支持设备绑定。下一版基础清单将全部声明：

```json
"doubleClickBehavior": "emit-device"
```

基础清单仍然不写正式 `deviceId`，`deviceMappings` 仍为空。平台只在运行时清单中注入当前绑定的 `deviceId`、二维节点引用和 `platformBindingCount`。

三个关键环节拓扑是总览的过滤视图，不复制节点和连线。它们会复用总览节点的设备标识、三维节点标识和绑定关系；同一个逻辑节点在总览和关键环节中只能对应同一个设备，不应被平台当成多台设备重复绑定。

## 三、问题二：发布清单排除设备能力

### 3.1 我方确认

0813 实际用途是燃气设备绑定联调包，不是纯视觉冒烟包。因此 `release-manifest.json` 排除 `device-mapping` 和 `device-states` 不符合本次交付目标，属于我方发布元数据错误。

### 3.2 下一版发布范围

下一版将从 `excludedCapabilities` 中移除：

```text
device-mapping
device-states
```

由于本次燃气包没有三维路径映射，`route-mapping` 可以继续排除；其余八个场景仍未交付，`other-eight-scene-content` 可以继续排除。README 将同步改为：燃气场景支持平台运行时设备绑定和设备四态，正式设备标识由平台注入，基础清单不写死设备标识。

平台运行时清单生成、设备绑定保存、设备状态完整快照和状态来源由平台负责；壳只校验并消费平台生成的完整运行时清单和状态消息。

## 四、事项三：独立服务部署与地址配置

### 4.1 正式部署方式

双方独立服务时，假设：

```text
平台父页面来源：      https://platform.example.com
我方可视化壳来源：    https://visual.example.com
```

我方构建或部署配置应按下表填写：

| 配置项 | 独立服务模式的含义 |
| --- | --- |
| `VITE_POWER_PARENT_ORIGIN` | 平台父页面的精确来源，例如 `https://platform.example.com` |
| `VITE_POWER_UNITY_PARENT_ORIGIN` | 我方可视化壳的精确来源，例如 `https://visual.example.com` |
| `VITE_POWER_UNITY_ENTRY_URL` | 我方服务提供的 Unity 入口，例如 `https://visual.example.com/unity/index.html` |
| `VITE_POWER_MANIFEST_URL` | 平台提供的运行时清单接口，或双方确认的受控代理地址 |

这里两个父源不能都填写 `${location.origin}`：平台是外层 `iframe` 的父页面，Unity 的直接父页面是我方可视化壳，二者在独立服务模式下不是同一个来源。

### 4.2 清单接口要求

如果浏览器直接从我方壳请求平台清单接口，平台接口必须：

1. 允许我方壳来源的跨域资源共享（`CORS`）；
2. 返回 `Cache-Control: no-cache`，保证绑定变化后不复用旧清单；
3. 在十秒内返回，或返回协议约定的错误结果；
4. 不依赖浏览器 Cookie，因为壳请求使用 `credentials: omit`；
5. 保持 `resourceKey`、清单版本、节点设备标识、设备映射和设备数量来自同一次绑定查询。

清单跨服务读取按照以上接口条件执行。平台不需要、也不应修改我方压缩后的脚本文件。

### 4.3 双方部署责任

我方负责：

- 以新配置构建或提供可注入运行配置的发布包；
- 正式构建使用双方确认的正式地址，不包含本地联调地址；
- 提供可访问的壳入口、Unity 入口和资源路径；
- 校验精确父源、清单版本和运行时清单结构。

平台负责：

- 提供平台父页面的精确来源和运行时清单接口地址；
- 允许平台页面嵌入我方壳，并授予全屏权限；
- 配置清单接口的跨域、缓存响应头、访问日志和反向代理；
- 不修改我方压缩脚本中的变量名或字符串来“临时修补”部署地址。

## 五、事项四：设备状态归一化口径

我方确认最终执行口径如下：

1. 单条状态项缺少必填字段、状态值非法或时间格式非法时，整条状态命令校验失败，不修改上一份状态。
2. 合法状态项的时间即使较早，也不能由壳自行判定为离线；完整快照按到达顺序直接应用。
3. 新的完整快照中没有上一批设备时，表示绑定关系发生变化；壳清除该设备的二维和三维动态状态，恢复基础状态，不显示为离线。
4. 只有平台明确发送 `deviceStatus: "offline"` 时，壳才显示离线。
5. 设备超过约定时间未更新的判断由平台完成，平台需要显式发送 `offline`；壳不自行计时、不根据请求失败或未收到新快照推断离线。

因此，协议中“缺少或过期状态归一为离线”的旧注释不能继续作为联调依据。我方会在后续文档和代码注释中改为上述口径。

双方联调按以上五点执行。“过期”只表示平台侧采集数据超时并由平台发送显式 `offline`，不表示壳把完整快照中缺少的设备自行判定为离线；如平台实现与此不同，应在联调前指出具体差异。

以下资料缺少时，我方无法继续进行正式的平台联调：

3. **设备状态测试入口或可发送的合法完整快照。** 至少包含一个已绑定设备，并能触发设备四态中的实际状态，用于验证二维拓扑和三维模型状态联动。

修正版联动包、我方壳地址、Unity 入口地址和基础清单由我方随新发布标识一并提供。
