# 关键环节异步生命周期稳定性设计

更新时间：2026-09-27

## 1. 背景与问题

Unity WebGL 在 Chrome 中执行场景或关键环节切换时，曾出现 `PlayerLoop internal function has been called recursively`（播放器主循环递归调用），随后触发 `RuntimeError: memory access out of bounds`（WebAssembly 内存越界）。

现有浏览器桥通过 `.jslib` 的 `SendMessage`（向 Unity 对象发送消息）同步进入 `UnityIframeBridgeManager.ReceiveFromParent`。该入口会在浏览器消息回调栈内直接执行场景切换、关键环节准备、提交、取消和资源释放。同时，新的关键环节准备可以取代尚未结束的旧准备事务，使两个资源加载流程短暂重叠。

## 2. 设计目标

- 浏览器回调只解析、校验和入队，不在外部回调栈内改变 Unity 场景或资源状态。
- Unity 每帧按接收顺序处理有限数量的命令，禁止递归进入播放器主循环。
- 任意业务场景任意时刻最多存在一个关键环节资源加载任务。
- 新准备事务必须先取消旧事务，并等待旧事务完成安全收尾后再开始加载。
- 取消只标记所有权失效；实际实例和资源租约由拥有它们的加载协程统一释放且只释放一次。
- 保持第二版网页图形协议、动作标识、场景清单、拓扑映射和现有用户交互不变。

## 3. 状态与不变量

关键环节准备状态：

```text
Idle（空闲）
  └─ prepare → Loading（加载中）
       ├─ success → Prepared（已准备）
       ├─ abort → Cancelling（等待安全取消）→ Idle
       └─ newer prepare → Cancelling → 新事务 Loading

Prepared
  ├─ commit → Active（已激活）
  ├─ abort → Idle
  └─ newer prepare → 释放旧候选 → Loading
```

必须始终成立：

1. `activeLoadCount <= 1`。
2. 只有当前准备事务可以写入候选槽。
3. 过期事务只能释放自身迟到结果，不能移动相机、阻断交互或覆盖活动实例。
4. 每个 `ProcessDetailLoadHandle`（关键环节加载句柄）和底层资源租约最多释放一次。
5. 浏览器消息回调不得直接调用场景切换、实例化、销毁或 AssetBundle（资源包）卸载逻辑。

## 4. 实现方案

### 4.1 浏览器命令帧队列

`ReceiveFromParent` 保留协议解析、实例标识校验和加密负载解码，随后将已验证命令写入有界先进先出队列。`Update` 在 Unity 自身播放器帧内按顺序取出并执行命令。

队列设置固定容量和单帧处理上限，避免恶意或异常调用方通过消息洪泛造成无界内存增长或长帧。释放开始后清空未执行命令；重复释放仍沿用原有幂等响应。

### 4.2 单在途准备事务

`ProcessDetailCoordinator` 为正在执行的准备任务保存独立操作对象，包含代际、事务标识、候选运行时、取消状态和完成状态。

新事务到达时：

1. 标记旧事务取消。
2. 逐帧等待旧事务的加载枚举器退出并完成资源清理。
3. 旧事务完成后，新事务才获得唯一加载权。

取消命令不再从外部回调中强制终止枚举器或释放仍可能被异步操作引用的对象。加载协程恢复后检测取消状态，清理迟到句柄并返回 `process-detail-prepare-superseded`。

## 5. 兼容性

- 不增加、删除或重命名任何公开命令。
- 不修改 `transitionId`（事务标识）语义。
- 正常准备、提交、退出和播放控制结果保持不变。
- 唯一可观察时序变化是命令至少延迟到后续 Unity 帧执行；该延迟通常小于一个显示帧，并处于现有协议超时预算内。
- 快速连续点击时仍以最后一个有效事务为准，但不会并发加载多个关键环节资源。

## 6. 测试与发布门禁

测试驱动开发要求先覆盖：

- 浏览器命令在 `ReceiveFromParent` 返回前不得产生业务响应。
- 第二个准备事务在首个加载安全结束前不得调用加载器。
- 被取代和被取消的迟到实例均销毁，资源租约各释放一次。
- 正常准备、提交、直接切换、退出、状态重放和相机恢复保持通过。

本次不改变场景发布契约。Unity 脚本修改后如需生成测试包或正式包，必须使用新的唯一 `unityReleaseId`，不得覆盖或复用旧 Unity 发布目录。
