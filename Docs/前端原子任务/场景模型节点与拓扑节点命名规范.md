# 场景模型节点与拓扑节点命名规范

**适用范围：** 九个 Unity 业务场景、全部二维拓扑、结构清单、平台内部节点绑定、动作映射和三层联调。  
**状态：** 命名基线已确定，后续新增节点必须遵守；燃气既有节点按本文遗留规则冻结。  
**更新时间：** 2026-08-14。

> **最新会议修正：** `nodeId` 是平台与我方共同使用的唯一逻辑关联键。平台自行维护 `nodeId → 真实设备编号`，不向我方注入 `deviceId`；我方清单、消息、状态缓存和三维反向选择都不依赖真实设备编号。文中旧的“运行时清单注入”表述只代表历史实现。

## 一、结论

1. Unity 游戏对象（`GameObject`）名称、三维节点标识（`sceneNodeId`）和二维节点标识（`nodeId`）是我方三类字段；平台真实设备标识（`deviceId`）只存在于平台内部，禁止进入我方协议或与节点编号互换职责。
2. 三维节点的完整唯一键是“场景标识（`sceneId`）＋三维节点标识（`sceneNodeId`）”；二维节点的完整唯一键是“拓扑标识（`topologyId`）＋二维节点标识（`nodeId`）”。
3. `nodeId` 与 `sceneNodeId` 可以使用相近的业务语义尾段方便人工审阅，但即使文本完全相同，也必须通过结构清单中的 `sceneNodeId` 字段显式映射。
4. 中文名称只写入 `title` 或 Unity 编辑器显示名。稳定标识发布后不得因中文文案、模型文件名、层级位置或图面布局变化而修改。
5. 结构清单不得写入正式 `deviceId`。平台只读取 `nodeId` 并在平台内部维护设备绑定，不得改写我方节点命名。
6. 燃气场景当前已验证的三维节点标识属于冻结遗留接口，不为追求格式统一而直接批量改名；其余八场景没有正式节点资料时不得预造名称。

## 二、四类名称的职责

| 名称 | 事实来源 | 唯一性范围 | 是否进入协议 | 是否允许从其他名称推导 |
| --- | --- | --- | --- | --- |
| Unity 游戏对象名称 | Unity 场景作者或导入模型 | 仅用于编辑器阅读，不作为业务唯一键 | 否 | 否 |
| `sceneNodeId` | Unity 场景映射与控制器登记 | 同一 `sceneId` 内唯一 | 是 | 否 |
| `nodeId` | 联动资源结构清单 | 同一 `resourceKey` 内全局唯一 | 是 | 否 |
| `deviceId` | 合作方平台内部设备主数据 | 由平台自行维护 | 否，不进入我方协议 | 否 |

Unity 场景文件名、预制体名、模型名、对象层级路径、文件编号、全局唯一标识符（`GUID`）、运行时实例编号和二维坐标均不属于稳定映射事实。

## 三、稳定标识公共格式

除平台 `deviceId` 外，我方稳定标识统一满足：

```text
^[a-z][a-z0-9_]*(?:[.-][a-z0-9_]+)*$
```

补充约束：

1. 总长度为1至128个字符；大小写敏感。
2. 新标识优先使用小写英文字母、数字、点号和短横线，不再新增下划线风格；下划线只为兼容已发布标识保留。
3. 点号表示稳定语义层级；短横线只连接一个业务词组，例如 `gas-turbine`、`grid-output`。
4. 实例号优先使用经业务资料确认的编号。没有正式编号时可使用从1开始、不补前导零的十进制序号；序号一经发布不得因数组排序或场景层级调整而变化。
5. 禁止中文、空格、大小写混用、斜杠、反斜杠、文件后缀、网址、随机值、时间戳、坐标和临时词。
6. 禁止使用 `node1`、`temp`、`test`、`new`、`copy`、`unknown` 等不能表达稳定业务含义的正式名称。

平台设备标识（`deviceId`）的格式和唯一性由平台自行负责；我方不校验、不缓存、不转发该字段。

## 四、拓扑和二维节点命名

### 4.1 拓扑标识

拓扑标识（`topologyId`）全局唯一，格式为：

```text
topology.<sceneId>.<view-purpose>
```

示例：

- `topology.gas-power.overview`
- `topology.substation.primary-system`
- `topology.microgrid.energy-flow`

`view-purpose` 描述稳定业务视图，不使用“页面一”“新版”“大屏”等界面临时名称。

### 4.2 二维节点标识

二维节点标识（`nodeId`）在同一 `resourceKey` 内全局唯一，新节点使用：

```text
<kind>.<business-role>[.<instance>]
```

固定类别（`kind`）：

| 类别 | 用途 | 格式示例 |
| --- | --- | --- |
| `asset` | 可确认的设备、装置或物理资产 | `asset.gas-turbine.1` |
| `system` | 控制、信息、保护或业务系统 | `system.ems` |
| `group` | 只用于分组或汇总的概念节点 | `group.unit-control` |
| `endpoint` | 外部系统、边界或送入送出端点 | `endpoint.grid-output` |
| `virtual` | 经正式资料确认、但没有单一物理对象的逻辑节点 | `virtual.energy-balance` |

规则：

1. 节点移动到其他展示层、坐标变化、图标变化或中文标题变化时，`nodeId` 不变。
2. 同一业务实体出现在多套拓扑时，必须复用同一个逻辑 `nodeId`；关键流程过滤视图只引用总图节点，不复制定义。平台内部设备绑定也只认该 `nodeId`，不认标题或字符串猜测。
3. 一个二维节点最多声明一个 `sceneNodeId`；没有三维联动时省略该字段，禁止填写空字符串。
4. 概念分组节点不得为了获得三维效果而伪装成物理设备节点。

## 五、Unity 模型与三维节点命名

### 5.1 Unity 游戏对象名称

Unity 游戏对象名称只用于编辑器阅读，不进入外部协议。新增我方包装对象建议使用可读英文名称：

```text
<BusinessRole>_<Instance>
```

例如 `GasTurbine_1`、`Hrsg_1`、`GridOutput`。场景根层建议使用 `SceneRoot`、`Environment`、`Equipment`、`Runtime`、`Effects`、`Cameras` 等固定职责名称。

导入模型的子对象名称、骨骼名称、动画名称和材质名称默认保留，避免破坏预制体、动画或材质引用。无论对象是否改名或移动层级，对外协议都只使用独立登记的 `sceneNodeId`。

### 5.2 三维节点标识

三维节点标识（`sceneNodeId`）在所属 `sceneId` 内唯一，不重复写入 `sceneId`。按逻辑目标类型使用以下格式：

| 目标类型 | 格式 | 示例 |
| --- | --- | --- |
| 可聚焦物理节点 | `node.<business-role>[.<instance>]` | `node.gas-turbine.1` |
| 机组或子系统聚合 | `unit.<technology>.<instance>.<subsystem>` | `unit.ccgt.1.gas-train` |
| 厂级或场景级聚合 | `plant.<business-role>` | `plant.overview` |
| 经确认的虚拟热点 | `hotspot.<business-role>[.<instance>][.<part>]` | `hotspot.hrsg.1.drum` |

规则：

1. 一个 `sceneNodeId` 可以显式绑定一个或多个 Unity 游戏对象或渲染器，用于聚合聚焦、显隐和状态处理。
2. 一个可点击 Unity 对象只能有一个规范回传的 `sceneNodeId`；禁止依赖序列化数组的先后顺序解决多重归属。
3. 分组节点可以与物理节点共享部分目标对象，但必须明确哪些节点允许反向选择；没有唯一回传目标时不得上报对象选择事件。
4. `sceneNodeId` 必须登记在当前场景的 `unitySceneMappings.sceneNodeIds` 中，动作、二维节点和控制器只能引用已登记值。
5. `sceneNodeId` 表示 Unity 对外暴露的稳定逻辑目标，可以对应对象组或热点，不要求等于任何游戏对象名称。

## 六、二维与三维映射规则

1. 映射只写在基础拓扑节点的可选 `sceneNodeId` 字段中，禁止根据标题、位置、图标、对象名或字符串相同自动生成。
2. 同一场景不同拓扑中的多个 `nodeId` 可以显式引用同一个 `sceneNodeId`；壳按目标去重。
3. 同一拓扑中多个二维节点引用同一个三维目标时，必须有明确业务理由，并通过选择、状态和反向选择回归。
4. 一个 `nodeId` 最多显式引用一个 `sceneNodeId`；有映射时同步三维，无映射时只更新二维。
5. 同一场景内一个 `sceneNodeId` 最多反向对应一个 `nodeId`；冲突时结构清单发布校验失败。
6. `nodeId`、`sceneNodeId` 和平台内部 `deviceId` 即使文本相似也不得互换字段职责。

格式示例仅用于说明，不代表正式燃气映射已经改变：

| Unity 编辑器对象 | `sceneNodeId` | `topologyId` | `nodeId` | 中文标题 | 平台内部绑定 |
| --- | --- | --- | --- | --- | --- |
| `GasTurbine_1` | `node.gas-turbine.1` | `topology.gas-power.overview` | `asset.gas-turbine.1` | 燃气轮机 | 平台按 `nodeId` 自行绑定 |
| `EMS` | 无 | `topology.gas-power.overview` | `system.ems` | 能量管理系统 | 平台按 `nodeId` 自行决定 |
| 无单一对象 | 无 | `topology.gas-power.overview` | `group.enterprise-layer` | 企业信息层 | 平台自行决定是否建立业务关系，我方不接收设备号 |

## 八、改名与版本策略

1. 中文标题或 Unity 游戏对象显示名修改，不要求变更稳定标识。
2. 已发布 `nodeId` 或 `sceneNodeId` 原则上禁止原地改名；业务实体语义确实变化时按破坏性变更处理。
3. 改名必须在同一发布事务中同步更新 Unity 控制器登记、`unitySceneMappings`、基础拓扑、动作引用、流程引用、测试夹具、清单版本、场景映射版本和资源版本。
4. 平台需基于新结构清单刷新内部 `nodeId` 绑定；绑定变化不改清单版本，也不得要求我方接收设备号。
5. 当前协议没有节点别名或重定向字段，不能只改一侧，也不能长期保留两个指向同一目标的伪别名。
6. 每次确需改名时必须提供“旧标识、规范新标识、变更原因、影响引用、版本、确认人、验证日期”迁移表。

## 九、发布校验清单

- [ ] `topologyId` 符合格式且全局唯一。
- [ ] `nodeId` 符合格式、长度限制，并在同一 `resourceKey` 内全局唯一；过滤视图复用源节点。
- [ ] `sceneNodeId` 符合格式、长度限制，并在所属场景内唯一。
- [ ] Unity 每个三维节点绑定至少一个有效目标；重复标识不会后写覆盖。
- [ ] 每个可点击对象只有一个规范回传三维节点。
- [ ] 所有二维到三维关系均显式声明，未使用标题、对象名、层级路径或坐标推断。
- [ ] 结构清单没有 `deviceId`、`deviceMappings`、`platformBindingCount` 或绑定修订字段。
- [ ] 每个 `nodeId` 最多映射一个 `sceneNodeId`，每个 `sceneNodeId` 最多反向对应一个 `nodeId`。
- [ ] 标题或 Unity 层级调整不会改变稳定标识。
- [ ] 改名时所有清单、Unity资源、映射和版本已原子升级。

双端格式、长度、唯一性、可点击对象多重归属和节点主键迁移的自动门禁归任务-049、051、056实施；本文件先固定命名事实，不提前伪造其余八场景节点。
