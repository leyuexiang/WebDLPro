# 任务-038：设备状态批量协调与可观测性实施状态

**状态：** 进行中（80%）
**更新时间：** 2026-08-09

## 已实施

- `DeviceStatesUpdateCoordinator`（设备状态批量协调器）接收已通过外层协议校验的 `device.states.update`（设备状态批量更新）。二维部分立即调用唯一 `TopologyRuntime`（拓扑运行时）的增量缓存；三维部分不再逐条外层消息发送，而是在同一动画帧中按 `sceneNodeId`（三维节点标识）仅保留最后一条状态后下发。
- `TopologyDeviceStateCache`（拓扑设备状态缓存）除保留活动场景完整状态快照外，新增“本批已接受、属于当前 Unity 场景”的三维节点增量快照。增量携带规范化 UTC ISO `statusUpdatedAt`（状态更新时间），不携带父页面原始载荷、设备名称或 Unity 对象信息。
- 同一动画帧中的旧节点状态被新状态覆盖时，只发送最终状态；每个外层批次仍独立等待最终节点回执。这样既满足“同设备同帧只处理最新状态”，也不会把二维已提交、三维未确认的部分成功伪装成成功。
- Unity 状态下发继续使用最多八路的受限工作池；动画帧等待批次上限同样为 64，严格不超过内层连接器的 64 条待确认容量。单个节点失败只影响关联批次，其他节点继续下发。
- 内层 `setNodeVisualState`（设置节点视觉状态）结构版本已升级为 2，必填 `statusUpdatedAt`、`hasSourceRevision` 和 `sourceRevision`。网页图形协议、运行时端口、本地 Unity 模拟页和 `UnityIframeBridgeManager`（Unity 内嵌框架桥接管理器）均校验这一复合因果二元组；缺失、不可解析、负数或超过 JavaScript 安全整数上限的修订不能进入当前场景控制器。
- Unity 桥按当前活动控制器和 `sceneNodeId` 保存固定 500 项因果水位。更早时间、同时间低修订和同一命令重试均返回成功但不重复调用控制器；只有控制器成功应用状态后才推进水位，活动控制器变化或整体释放时统一清空。
- 释放时会取消尚未开始的动画帧、结算所有等待批次为 `runtime.disposed`（运行时已释放）、清空待下发节点和固定容量诊断。已在路上的 Unity 命令无法物理撤回，但其迟到回执不能再写诊断或完成旧外层命令。
- 诊断仍为固定 64 条先进先出队列，只保存关联标识、处理时间、耗时、接受/过期/无映射/无效时间计数、Unity 目标/成功/失败/能力不可用计数；新增 `unityFrameMergedCount`（动画帧合并计数），不保存完整状态消息、设备标识、三维节点标识、异常对象或 Unity 层级路径。
- `HostRuntimeComposition`（宿主运行时组合根）只在协调器实际注入时声明 `device.states.update` 能力。二维状态、三维状态、状态缓存、画布和 Unity 内嵌框架仍保持隔离，外层桥不直接访问任何渲染对象。
