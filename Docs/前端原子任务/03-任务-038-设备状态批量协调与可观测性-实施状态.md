## 合作方契约变更结论

- 二维完整快照提交是 `device.states.update` 的唯一外层成功边界。载荷合法且二维提交成功后必须立即返回一次成功结果，不等待 Unity 最终回执。
- 运行时映射存在 `sceneNodeId` 时必须尝试三维状态同步，但该路径属于异步尽力交付。Unity 未就绪、能力缺失、单节点失败、超时、容量拒绝或释放竞争只进入有限内部诊断，不撤销二维，不改变、补发或延迟外层成功结果。
- 当前实现已移除“每个外层批次等待三维最终回执”与“按状态时间、平台来源修订拒绝状态”的旧规则。二维提交后立即结算唯一成功；三维仅异步尽力投递，平台来源字段不参与覆盖顺序。
- 结构清单没有 `deviceMappings` 是正确交付边界，不再视为缺陷；正式三层验收使用我方不可变结构清单，平台内部绑定不进入壳侧状态链路。

## 已实施且可复用

- `DeviceStatesUpdateCoordinator`（设备状态批量协调器）已隔离二维与三维端口；二维完整快照原子提交后立即返回唯一外层成功。三维采用“一个待发送完整快照槽位 + 最多八路工作池”，同一动画帧只保留最新权威快照，既不阻塞外层也不无界积压。
- `TopologyDeviceStateCache`（拓扑设备状态缓存）除保留活动场景完整状态快照外，新增“本批已接受、属于当前 Unity 场景”的三维节点增量快照。增量携带规范化 UTC ISO `statusUpdatedAt`（状态更新时间），不携带父页面原始载荷、设备名称或 Unity 对象信息。
- 同一动画帧中的旧节点状态被新状态覆盖时只发送最终状态的性能机制可以保留；“每个外层批次等待最终节点回执”属于旧契约，必须移除。
- Unity 状态下发使用最多八路的受限工作池，且仅保留一个尚未发送的快照槽位；单个节点失败只写当前有限诊断，其他目标继续下发。
- 内层 `setNodeVisualState`（设置节点视觉状态）已升级为结构版本3，字段为 `sceneNodeId`、`visualState`、`snapshotSequence`、`statusUpdatedAt`、`sourceRevision`；独立 `clearNodeVisualState`（清除节点视觉状态）结构版本1用于设备从完整快照消失时恢复模型基础视觉。`hasSourceRevision` 已移除，防止其被误用为因果门禁。
- Unity 桥按当前活动控制器和 `sceneNodeId` 保存固定500项本地快照序号水位；小于或等于已应用序号的设置、清除命令幂等成功且不调用控制器。场景激活、控制器变化或整体释放会清空旧代次水位；来源时间和平台修订只作诊断。
- 释放时会取消尚未开始的动画帧、清空待下发节点和固定容量诊断。重构后释放只取消未执行的三维内部任务，不能反向修改已经完成的外层二维成功结果。
- 诊断仍为固定 64 条先进先出队列，只保存关联标识、处理时间、耗时、接受/过期/无映射/无效时间计数、Unity 目标/成功/失败/能力不可用计数；新增 `unityFrameMergedCount`（动画帧合并计数），不保存完整状态消息、设备标识、三维节点标识、异常对象或 Unity 层级路径。
- `HostRuntimeComposition`（宿主运行时组合根）只在二维完整快照链路实际可用时声明 `device.states.update` 能力；该能力不依赖 Unity 是否声明四态视觉能力。二维状态、三维状态、状态缓存、画布和 Unity 内嵌框架继续保持隔离。
