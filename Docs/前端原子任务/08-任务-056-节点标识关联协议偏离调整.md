## 一、最新有效结论

1. 我方只向平台提供稳定的拓扑节点编号 `nodeId`，不接收、不保存、不转发平台真实设备编号 `deviceId`。
2. 平台读取我方结构清单中的 `nodeId`，并在平台内部维护 `nodeId -> 真实设备编号` 的绑定关系；该关系不注入我方清单。
3. 双击拓扑节点时，外层事件类型继续使用 `topology.node.dblclick`，载荷改为 `sceneId + topologyId + nodeId`，不得再包含或等待 `deviceId`。
4. 状态命令继续沿用既有 `device.states.update` 信封、完整快照、四态、`sourceRevision`、到达顺序替换、容量限制和回执语义；每个状态项的关联键从 `deviceId` 改为 `nodeId`。
5. 二维状态提交仍决定外层成功回执。存在 `sceneNodeId` 映射时必须异步尝试同步三维；三维失败、超时或部分失败仍不得改变、延迟、撤销或补发外层成功回执。
6. 我方结构清单直接作为壳运行依据，不再等待平台生成“注入设备编号后的运行时清单”。`deviceMappings` 和 `platformBindingCount` 退出前端清单模型。
7. `nodeId -> 可选 sceneNodeId` 是二维与三维之间唯一允许的静态映射。不得按标题、坐标、图标、模型名称或设备编号猜测三维目标。

## 二、节点编号新约束

状态项只携带 `nodeId`，因此 `nodeId` 必须在同一个联动资源 `resourceKey` 范围内全局唯一，而不再只是单张拓扑内唯一。

- 九个场景的新节点采用“场景业务前缀 + 节点语义”命名，避免不同场景出现相同短编号。
- 关键流程子图必须引用总图中的同一逻辑 `nodeId`，不能复制出另一个编号。
- 过滤视图重复显示同一节点不算重复定义；它只是引用源拓扑节点。
- 一个 `nodeId` 最多登记一个 `sceneNodeId`。
- 一个 `sceneNodeId` 在同一场景内最多反向对应一个逻辑 `nodeId`；否则三维反向选择无法确定应上报哪个节点。
- 若合作方以后要求允许资源内重复 `nodeId`，状态项必须同时增加 `sceneId` 或 `topologyId` 形成复合键，不能在当前仅有 `nodeId` 的载荷上猜测。

## 三、迁移前偏离基线（历史）

| 链路 | 现有实现 | 新目标 | 风险 |
| --- | --- | --- | --- |
| 清单模型 | 节点可含 `deviceId`，根级含 `deviceMappings`、`platformBindingCount` | 清单只含结构节点和可选三维映射 | 旧运行时清单校验会阻止启动 |
| 双击能力 | `emit-device` 且节点无 `deviceId` 时静默 | 改为节点上报能力，双击直接发送 `nodeId` | 只改载荷会被旧守卫丢弃 |
| 状态主键 | `Map<DeviceId, 状态>` | `Map<NodeId, 状态>` | 二维与三维可能继续按旧设备号错投 |
| 状态投影 | `deviceId -> deviceMappings -> nodeId -> sceneNodeId` | `nodeId -> 二维节点 + 可选 sceneNodeId` | 旧映射表删除不完整会留下双重事实源 |
| 三维反向选择 | `sceneNodeId -> deviceId -> topologyNodeRefs` | `sceneNodeId -> nodeId` | 旧组合根会拒绝无设备号的事件 |
| 清单获取 | 平台生成完整运行时清单，壳远程读取 | 我方不可变结构清单直接运行，平台只读节点编号 | 合作方包仍调用旧接口会启动失败 |
| 发布门禁 | 要求23个 `emit-device` 节点、设备映射能力和绑定计数 | 要求节点编号唯一、无设备字段、节点事件与节点状态能力 | 旧门禁会误拒绝新包 |
| 平台责任 | 注入设备编号、二维引用和绑定计数 | 仅在平台内部绑定节点与真实设备 | 旧交接说明会让合作方重复开发 |
