### 进度状态定义

| 状态 | 使用条件 |
| --- | --- |
| 未开始 | 尚未进入实现或资料准备 |
| 进行中 | 已开始，但至少一项验收要求未完成 |
| 已完成 | 全部验收要求通过，证据已记录 |
| 待外部资料 | 被美术、平台或合作方资料阻塞，但方案和边界已明确 |
| 阻塞 | 相同阻塞条件已连续复现，且当前无法通过安全替代方案推进 |
| 暂缓 | 用户明确要求暂不实施，不等同于已完成 |

### 更新规则

1. 每个任务只能有一个当前状态。
2. “已实现”不等于“已完成”；必须同时满足需求、边界和验收要求。
3. 外部资料缺失时标记“待外部资料”，在备注中写明缺失项、责任方和解除条件。
4. 一个任务出现范围变化时，先更新任务边界，再继续实现，禁止在代码中临时扩大范围。
5. 验收证据至少记录资源版本、场景版本、浏览器、硬件、测试时间和结果摘要。
6. 如果发现任务无法独立验收，应在不修改已完成任务边界的前提下拆出新任务，不直接把新需求塞入当前任务。

## 二、执行总原则

- 所有绑定使用稳定 ID，不使用模型名称、文件名、层级路径或坐标猜测。
- 第一层只放九个代表性建筑低模和必要的管道、区域效果，不放九个完整业务场景设备。
- 第一层只有异常状态才触发停流和区域效果，正常状态不配置影响效果；其他状态保留扩展入口。
- 区域正式效果只实现半透明区域覆盖和静态区域边界；粒子、脉冲和扫描线不进入第一版默认实现。
- 模型异常、告警、描边、内部颜色和闪烁继续使用现有高亮插件。
- 透明、不透明、流动等渲染模式由少量共享材质变体负责；颜色、透明度、闪烁和流速由材质属性块负责。
- 厂房可以是一个 Mesh、多个材质球，只做整体控制，不做局部墙体和屋顶控制。
- 厂房壳体资源加载后常驻；点击厂房后按需加载第二层整套内部设备，进入内部时只隐藏或整体半透明壳体。
- 第一层沙盘只显示占满子应用可视区的三维画面；第二层厂区和第三层关键环节均同时显示三维画面与拓扑图。
- 所有第二层业务场景的三维容器顶部正中默认显示统一横向管线图例；图例默认缩小到约 420 像素宽并保持 500×60 原始比例，正常显示、进入全屏、全屏中和退出全屏后均保持可见。该图例没有点击、拖拽、悬停或状态切换效果，也不阻断下方三维交互；第一层与第三层不显示。
- 第三层按业务场景配置 0～多个关键环节，不写死每场景三个；当前首批仅燃煤、燃气各三套。
- 关键环节命令由 `workflow.trigger → actionId → processDetailId` 显式映射到新增白名单命令，只加载当前目标三维资源，并将相机切换到远离厂区的显式观察位；提交时保留所属第二层 `topologyId` 作为画布及渲染器归属，并通过 `topologyDataContextId` 加载当前关键环节完整拓扑数据文件，在同一画布中保持双区布局。不得通过第二层拓扑过滤、凸显第二层单个模型或隐藏其他模型代替第三层拓扑。
- 第三层允许为每个关键环节新增独立拓扑 JSON 数据文件，但不得新增第二套画布、专属图元组件或重复图片目录；图元注册、公共四态图片、装饰资源、图片缓存、选择高亮、设备提示和公共重置入口均与第二层共用。
- 第二层保留架构层、网络层、业务层、关键环节层及已明确提供的组合层文件切换；架构层与其他层互斥。每种选择直接加载对应输入文件，不在浏览器中裁剪、拼装或逐图元过滤。
- 第三层不显示层级筛选入口，也不接受残留、键盘或程序触发的层级筛选事件，只显示当前 `processDetailId` 对应的完整关键环节拓扑。
- 关键环节状态先进入缓存，模型加载完成后重放最新快照；故障状态停止管道流动、模型动画和粒子特效，其他状态或状态缺失时启动播放。
- 第三层三维模型与可见拓扑从同一中央 `nodeId → 状态` 快照同步；切换数据上下文后必须在首次正式重绘前重放提交时的最新状态，加载期间到达的新状态不得丢失。
- 第三层动态效果使用状态驱动控制器；故障停止，其他状态或状态缺失时播放。模型自身点击不产生播放或停止控制效果。
- 同一实例默认最多激活一套关键环节资源；切换、返回、失败和释放均必须清理句柄、动画、粒子和状态绑定。
- 五个页面独立接收平台状态，不要求平台方提供共享连接。
- 不在本次重构中强制引入 Addressables（可寻址资源系统），优先延续现有 AssetBundle（资产包）方案。
- 第一版 `/gas-topology-json-preview` 已完成外部存档并从项目移除；当前第三版预览 `/gas-v3-topology-json-preview` 与正式总览使用同一数据和交互实现，不得恢复第一版路由或资源依赖。

### R-015：第三层关键环节可变数量目录与资源组织

**需求：**

新增独立于第二层整套内部设备和 `ThreeLayerBindingCatalog` 的关键环节目录及加载资源边界。每个业务场景允许配置 0～多个关键环节；当前首批登记燃煤三套、燃气三套，后续其他场景可按实际需求登记一套、两套或更多。

**边界：**

- 不修改九项业务 `sceneId` 闭集，不把关键环节注册为新场景。
- 不复用第二层唯一 `detailResourceId` 表达第三层列表。
- 目录只接受显式 `sceneId / processId / stepId / processDetailId / processDetailResourceId / cameraPoseId / topologyId / topologyDataContextId` 映射；每个 `topologyDataContextId` 必须唯一解析到当前关键环节完整拓扑 JSON、来源散列、预期图元数量及 `nodeId → penId` 状态绑定。
- `topologyId` 必须属于同一业务场景，用于确定公共画布与渲染器归属；`topologyDataContextId` 指向关键环节独立拓扑数据文件。允许新增数据文件，禁止新增专属画布、图元组件、状态协议或重复公共图片目录。
- 同一实例默认最多激活一套关键环节资源；每套拥有独立加载句柄和释放边界。
- 目录容量设置合理上限，但不得写死每场景三个。
- 协调器和资源运行时必须消费目录项，不得写死燃气场景、燃气轮机、单一状态节点或单一动态目标。

**验收要求：**

1. 场景可合法登记 0、1、2、3 和更多关键环节。
2. 当前燃煤三套、燃气三套动作映射唯一，其他七个场景允许暂时为零。
3. 重复动作、重复 `processDetailId`、未知场景、未知资源、未知相机位、未知动态目标和跨场景引用被拒绝。
4. 关键环节资源失败、取消、切换和场景释放时句柄全部清理。
5. 正式目录不依赖模型名称、层级路径、文件名或坐标推断。
6. 目录、加载器和测试夹具不引用旧 `PowerPlantProcessController` 的显隐、包围盒聚焦或全场景管道控制；R-016 接通后第三层运行路径不得调用旧关键环节半透明逻辑，R-021 删除前必须完成静态引用审计。
7. 同一套运行时代码可驱动燃煤、燃气及后续其他场景，不为每个关键环节复制一套硬编码协调器。
8. 每个关键环节都能唯一解析到所属业务拓扑渲染器和独立拓扑数据文件；未知、跨场景、散列或图元数量不符的映射必须拒绝，禁止回退默认拓扑或按名称猜测。

**当前实施与纠偏记录（更新至 2026-09-06）：**

### R-016：第三层命令加载、远端相机与返回事务

**需求：**

收到新增白名单关键环节命令时加载目标细节资源，完成最新状态重放后将相机切换到远离所属厂区的专用观察位；网页保持同一 Meta2D 画布，在其中加载当前关键环节独立拓扑数据文件并继续使用三维与拓扑双区布局。第三层隐藏且阻断四层筛选；返回时恢复第二层拓扑文件、筛选状态和观察位，并释放第三层三维资源。外层仍通过 `workflow.trigger` 进入，但必须经 `actionId` 显式映射到 `processDetailId`，不得复用旧 `enterProcessStep`。

**推荐顺序：**

```text
workflow.trigger
→ 校验 actionId 并解析 processDetailId
→ 若当前不在目标场景，自动切换到目标业务场景默认拓扑并确认 sceneActivationId
→ 阻塞式重放目标场景最新权威设备状态
→ 调用新增白名单关键环节命令
→ 校验场景与关键环节映射
→ 加载目标资源但保持隐藏，并重放环节设备状态
→ 准备显式相机位
→ 在唯一 Meta2D 画布中准备当前关键环节独立拓扑数据文件
→ 读取提交时最新中央状态快照并批量应用到三维模型与拓扑
→ 原子提交关键环节数据上下文、双区布局和目标资源
→ 切换到关键环节专用相机位
→ 成功后释放上一套关键环节资源
```

**边界：**

- 不再通过凸显第二层单个模型并隐藏其他模型实现关键环节；旧 `enterProcessStep` 的显隐、相机复位和包围盒聚焦不得进入本事务。
- 关键环节稳定状态必须同时携带所属第二层 `topologyId` 与当前 `processDetailId`；画布显示当前关键环节独立拓扑 JSON，不显示第二层完整拓扑，不调用第二层四层筛选或浏览器端图元过滤。
- R-016 新链路通过验收后，旧关键环节半透明表现正式停用；停用不等于立即删除，R-021 需在历史二维兼容回归后删除无有效引用的旧第三层专用代码。
- 远端展示锚点、相机位置和旋转全部显式配置。
- 第二层整套内部设备可以保持已加载，但不得为切换第三层而全量遍历其 Renderer。
- 加载、独立拓扑文件校验、状态重放或相机准备失败时保留上一稳定三维视图、拓扑数据和状态。
- 第二层与第三层必须复用同一个画布组件、Meta2D 实例、图元注册、公共图片缓存、尺寸监听、事件监听和重置入口；首次进入某关键环节可加载并解析其独立 JSON，后续相同上下文应命中缓存。
- 数据上下文负责整体替换拓扑 JSON 数据；坐标、连线和布局以该输入文件为准，不在运行时过滤、裁剪或拼装。设备状态只能通过当前文件显式 `nodeId → penId` 绑定增量更新，禁止按标题、位置或数组顺序推断绑定。
- 第三层不得依赖停用整个第二层业务根节点完成空间隔离，必须使用显式远端展示锚点和专用相机位。
- 进入事务必须拆分为准备和提交两阶段；准备阶段保持目标资源隐藏且不移动相机，未提交的数据上下文不得覆盖当前拓扑；目标资源、数据绑定、最新状态和双区布局就绪后才原子提交资源、拓扑数据和相机。

**验收要求：**

1. 首批六个关键环节动作分别经 `actionId → processDetailId` 映射加载唯一正确资源并切换到正确观察位。
2. 关键环节画面中不会看到厂区模型与细节模型挤在同一空间。
3. 快速切换只提交最后有效事务，不产生多个活动实例。
4. 返回第二层后恢复相机、第二层拓扑文件、筛选选择、交互和状态；第三层三维资源释放，唯一画布和公共资源保持复用。
5. 失败、超时、场景切换和迟到回调不会覆盖新稳定视图。
6. 关键环节同时显示三维画面与其独立拓扑；允许关键环节 JSON 的图元、坐标、连线和布局不同，但画布实例、图元实现、公共图片、交互与状态链路不变。
7. 进入、切换和退出关键环节期间，不出现“关键环节三维画面 + 错误拓扑数据上下文”的可操作组合，也不重建唯一拓扑画布。
8. 已在第三层时可直接切换到同场景另一关键环节，不强制先返回第二层；新资源提交成功前保留旧稳定视图，成功后只保留一套活动实例。
9. 第二层业务根节点在第三层期间可保持加载，不以整体停用掩盖远端空间配置缺失。
10. Unity 的资源显示与相机切换不得早于独立拓扑数据、最新状态和无筛选双区布局提交。
11. 从沙盘或任意其他稳定业务场景触发已登记关键环节时，系统必须自动稳定目标业务场景并完成最新状态重放后进入第三层，不得要求用户手动预先进入对应场景。
12. 快速切换关键环节时只允许最后一次有效事务提交拓扑 JSON；过期数据请求不得覆盖当前画布或图元状态，失败事务不得污染公共拓扑缓存。
13. 首次进入关键环节允许请求其独立 JSON；相同上下文往返不得重复请求、重复图元注册、重复图片请求或增加事件监听器。
14. 第三层筛选组件不可见，筛选处理器对残留界面、键盘和程序事件均不响应；返回第二层后恢复原合法筛选状态。

**当前实施与纠偏记录（更新至 2026-09-01）：**

### R-017：第三层设备状态同步与故障视觉

**需求：**

将页面最新完整设备状态同时投影到当前关键环节细节模型和同一 Meta2D 画布加载的当前关键环节独立拓扑，使同一逻辑设备在第二层与第三层的三维、拓扑显示保持一致，并复用现有四态与高亮视觉。

**边界：**

- 模型加载完成前不显示未重放状态的设备。
- 缺失状态恢复基础视觉，不自动解释为离线。
- 每套关键环节可显式登记多个设备状态绑定；不得把整套模型压缩成单一 `stateNodeId` 后覆盖所有 Renderer。
- 正式视觉复用现有高亮能力表达描边、内部颜色和闪烁；材质属性块统一染色只允许作为资源或插件未就绪时的临时降级。

**验收要求：**

5. 切换环节、返回第二层和跨场景后无状态串场。
6. 一个关键环节内多个设备可独立显示不同四态，状态更新只访问已登记目标，不扫描完整模型层级。

8. 进入或切换关键环节后，当前独立拓扑在首次正式绘制前已应用最新状态；加载期间新状态不丢失，图标、提示文字和三维视觉无状态分裂或默认态闪烁。

### R-018：第三层状态驱动播放控制与动态资源生命周期

**需求：**

建立“统一协议层 + 统一生命周期基类 + 环节专用适配器 + 模型控制器”的第三层动态控制结构。3ds Max 导入的旋转/位移动画、环节内部管道流动和粒子特效由环节专用适配器显式登记并转换控制；设备为故障状态时停止受控动态效果，正常、告警、离线以及未收到状态数据时启动播放。播放和停止不绑定模型自身点击。

**统一控制链路：**

```text
ProcessDetailCoordinator
→ ProcessDetailDeviceBinding
→ IProcessDetailDynamicTarget
→ ProcessDetailDynamicTargetBase
→ 环节专用动态适配器
→ 具体模型控制器
```

**边界：**

- `ProcessDetailCoordinator` 和 `ProcessDetailDeviceBinding` 只负责统一状态聚合、实例事务与动态目标协议，不得引用具体场景、环节或模型控制器类型。
- 所有环节专用动态适配器必须实现 `IProcessDetailDynamicTarget` 并继承 `ProcessDetailDynamicTargetBase`，复用重复状态过滤、释放前停播和幂等释放，不得复制一套协调器或生命周期代码。
- 不在状态热路径扫描 Animator（动画状态机）、Animation（动画）、ParticleSystem（粒子系统）或 Renderer。全部受控目标和排除项在制作期显式序列化。
- 每个动态目标必须有稳定 `dynamicTargetId`；模型点击不承担播放或停止控制，不新增交互目标绑定。
- 任一已登记状态节点故障时，设备绑定器向全部受控动态目标下发 `playing=false, faultStop=true`；正常、告警、离线、状态清除或状态缺失时下发播放。历史播放命令只能重新应用当前状态结果，不能覆盖状态许可。
- 环节专用适配器可以显式配置不纳入统一控制的特效。排除列表默认必须为空；排除项由自身配置管理播放，不接收故障停播，但仍随关键环节根对象和资源句柄释放。
- 需要故障保留部分效果时，只能在环节专用适配器中显式实现或配置。例如燃气保留前端蓝色粒子，禁止把该例外写入统一绑定器或协调器。
- 隐藏加载阶段必须先重放最新状态并保存播放许可；实例激活后，模型自身 `playOnEnable`（启用时播放）不得覆盖预置故障停播结果。
- 重复状态更新保持幂等；切换、返回、失败和释放必须停止并清理受控动态对象、状态缓存与材质属性块。

**验收要求：**

1. 故障状态停止受控动画、粒子和管道流动；正常、告警、离线、状态清除及状态缺失时启动播放。
2. 状态重复更新和历史播放命令均不覆盖状态驱动结果，不重复创建控制器、材质、粒子实例或协程。
3. 点击模型自身不产生播放或停止控制效果，普通设备选择与相机交互不因该模型获得控制入口。
4. 切换、返回和释放后没有残留动画、粒子、材质属性块、碰撞监听或播放许可；非故障释放必须停止故障状态下被特例保留的效果。
5. 自测页不得再以 `normal` 模拟播放、以 `fault` 模拟停止；设备状态测试和动态播放测试必须分离。
6. R-016 起第三层不产生旧的其余模型半透明状态；R-021 完成静态引用审计并删除无有效引用的旧第三层专用代码。
7. 新增关键环节只需新增环节专用动态适配器并配置动态目标，不修改 `ProcessDetailCoordinator`、`ProcessDetailDeviceBinding` 或平台协议。
8. 排除列表为空时控制当前环节全部已登记特效；加入排除项后，故障状态不得暂停该效果，未排除效果仍按统一状态规则执行。
9. 预置故障先于模型激活到达时，模型首次显示必须保持停播；故障解除后自动恢复，不等待模型点击或额外播放命令。

**当前实施与纠偏记录（更新至 2026-09-06）：**

- 已新增 `ProcessDetailDynamicTargetBase`，统一实现重复状态过滤、退出前停播和幂等释放；`IProcessDetailDynamicTarget`、`ProcessDetailDeviceBinding` 和 `ProcessDetailCoordinator` 继续作为场景无关协议层。
- `GasTurbineProcessDetailDynamicAdapter` 已迁移到统一基类，并继续通过 `WaiKeHeBingMasterController` 控制燃机旋转、粒子、体积流动和电线信号。故障时保留前端蓝色粒子属于燃气专用例外，未进入统一控制层。

- `ControlValveEffectController` 已增加外部播放许可保存。隐藏候选阶段收到预置故障后，包装激活时不会被自身自动演示重新启动；故障解除后从当前状态恢复循环播放。

## 五、执行期间的防跑偏检查

每次开始一个任务前，先回答以下问题并记录在任务备注中：

1. 本任务修改的是哪一层：沙盘、第二层壳体、第二层整套内部设备、第三层关键环节、状态层还是发布层？
2. 本任务是否引入了新的业务 ID？如果引入，是否同步更新绑定表和清单校验？
3. 本任务是否改变了外部状态协议？如果改变，是否确实属于本计划范围？
4. 本任务是否把资源加载、视觉效果和业务影响关系耦合在一起？如果是，应重新拆分。
5. 本任务是否增加了每帧遍历、材质复制、粒子对象、协程或无限缓存？如果是，必须先说明容量和释放路径。
6. 本任务是否改变厂房从整体控制到局部控制的范围？如果是，必须新增任务，不得直接扩大 R-012。
7. 本任务是否把五个页面改造成共享连接或共享缓存？这不是当前方案的必要条件，必须单独评审。
8. 本任务是否依赖美术尚未确认的模型结构、UV 或材质属性？如果是，状态标记为“待外部资料”。
9. 本任务是否有可重复的验收步骤和证据位置？没有则不得标记为已完成。
10. 本任务是否把关键环节数量写死为三个，或假定所有场景数量相同？如果是，必须改成场景级可变列表。
11. 本任务是否仍通过凸显第二层单个模型并隐藏其他模型实现第三层？如果是，已偏离当前方案。
12. 本任务是否保持第三层统一状态驱动播放链路：协调器和设备绑定器只依赖 `IProcessDetailDynamicTarget`，专用适配器复用统一生命周期基类，故障停止、其他状态或状态缺失时播放，且模型点击不覆盖状态结果？如果没有，必须阻断验收。
13. R-016 起是否仍调用旧关键环节其余模型半透明、全量显隐、包围盒聚焦或全场景管道停控？如果是，必须阻断验收。
14. R-021 是否完成旧第三层专用代码的静态引用审计，并区分删除项与历史二维兼容保留项？未完成则不得封板。
15. 沙盘是否仍显示、激活或重绘拓扑，或第三层是否没有显示当前关键环节对应的独立拓扑数据？任一情况出现都已偏离当前三种视图模式。
16. 厂区是否同时保留三维画面和合法业务拓扑？如果任一被无故隐藏，必须阻断验收。
17. 第三层是否新建画布、复制公共图元组件或公共图片资源、停用整个第二层业务根节点，或在独立拓扑数据和最新状态提交前显示模型并移动相机？如果是，必须归入 R-016 纠偏。
18. 运行时是否写死燃气场景、燃气轮机、单一状态节点或单一动态目标，或把燃气、燃煤的特效例外写入通用协调器和设备绑定器？如果是，R-015、R-017、R-018 不得完成。
19. 第三层是否在运行时过滤、裁剪或拼装关键环节拓扑，是否修改输入 JSON 的坐标、连线或资源地址，或按标题、位置、文件名推断绑定？如果是，必须阻断验收。
20. 第三层三维模型与当前关键环节独立拓扑是否读取同一中央状态快照，并在首次正式绘制前同步？如果没有，R-017 不得完成。
21. 第二层三维容器是否缺少公共管线图例、全屏往返后图例消失、图例阻断三维操作，或第一层与第三层误显示图例？任一情况出现都必须阻断 R-014 和 R-021 验收。
22. 新关键环节是否通过专用动态适配器显式登记全部受控目标和排除项，并验证隐藏加载预置故障、故障解除、重复状态、直接切换和释放？如果没有，R-018 不得完成。
23. 第二层是否只加载明确提供的层级组合文件并遵守架构层互斥；第三层是否仍显示或响应四层筛选？任一不符合均阻断验收。
