# 发布门禁与打包交付

## 1. 发布身份和包类型

每次发布都生成不可变发布标识（`releaseId`），并在同一次构建中固定：`manifestVersion`、Unity 构建标识（`buildId`）、`sceneMappingVersion`、各场景 `resourceVersion`、拓扑/动作 `configVersion`、协议版本和资源摘要（`resourceDigest`）。版本不一致时拒绝拼接旧缓存运行。

| 包类型 | 用途 | 必须包含 | 禁止包含 |
| --- | --- | --- | --- |
| `local-test` | 本地浏览器回归 | 自测页、结构清单、Unity 资源、诊断入口 | 未验证外部来源配置 |
| `partner-integration` | 合作方联调 | 结构清单、Unity 资源、公开协议入口 | 自测页、网页播放/停止控件、平台设备号 |
| `standalone-formal` | 正式部署 | 联调包运行资源和协议契约 | 调试入口、测试夹具、可变外部清单地址 |

当前约定端口：`partner-integration` 联调包使用 5575，`local-test` 本地测试包使用 5523；正式环境以部署配置为准，不把本机地址写入公开来源。

## 2. 变更前审计

在仓库根目录执行并保存输出：

```powershell
node .agents/skills/scene-release-gate/scripts/inspect-release-contract.mjs
```

同时检查工作区已有修改，列出本次新增/删除/修改的场景、动作、关键环节、节点、映射和拓扑文件。不得回退或覆盖无关改动。

## 3. 源生成器和清单同步

所有发布能力回到源生成器实现，不能手改历史发布目录或打包后的 JSON。核心同步关系：

1. `scene-topology-manifest.json` 的 `actions` 登记全部公开动作。
2. 每个场景 `supportedActionIds` 反向包含且只包含目标场景动作。
3. `processDetails` 与第三层动作一一对应，资源、相机、状态节点和拓扑上下文齐全。
4. `unitySceneMappings` 只登记已核验的节点、步骤和路线。
5. `release-manifest.json.workflowActions` 与结构清单动作集合完全相同。
6. 拓扑变体、第三层上下文、`penId` 绑定、资源摘要和版本在同一事务生成。
7. 变电第三层必须通过 `tests/substation-topology-linkage-release-gate.spec.ts`：四类站点共 11 个关键环节逐项核对源 JSON 哈希、图元编号、业务 `nodeId`、三维 `sceneNodeId` 和公开动作；公共画布及四个站点包装器必须保留双向选中接口。

仅导航场景只能使用 `unityAction.type: none`，不要伪造流程、第三层或三维节点。当前 `inspect-release-contract` 输出的统计始终优先于历史文档数量。

## 4. 双层门禁

先做结构清单校验，再做最终产物门禁：

```powershell
cd power-data-web
npm run validate:manifest -- --manifest <工作区清单.json> --report <报告.json>
npm run validate:release-artifact -- --root <新发布目录>
```

绝对契约（预期能力校验）必须独立断言本次应发布的动作、场景边界、导航场景能力边界和第三层固定字段；相对一致性校验（清单互相比较）必须检查结构清单、发布摘要、场景反向引用、关键环节、三维映射和资源是否一致。两份清单同时漏项时，绝对契约仍要阻止发布。

发布门禁强制停止条件：动作只存在一侧、场景未反向声明、关键环节缺字段、仅导航场景伪造能力、自测绕过公开动作、核心文档与当前清单漂移、最终目录未校验或校验失败。

## 5. 测试与自测入口

按变更范围执行专项测试，再执行全量检查：

```powershell
npx vitest run tests/configured-power-scenes-manifest.spec.ts tests/substation-topology-linkage-release-gate.spec.ts tests/release-artifact-contract.spec.ts
npm run test:unit
npm run typecheck
npm run build
```

涉及第三层时，读取并执行当前 `audit-process-detail-production.mjs` 的生产审计。自测页必须使用合作方公开的 `workflow.trigger` 和稳定 `actionId`，禁止使用内部 `view.open` 捷径代替验收。

至少验证：场景进入、默认拓扑、二维选择、三维聚焦、三维反选、完整四态、相机复位、场景复位、第三层进入/退出、释放、快速切换、超时、迟到回执、版本冲突和资源失败。

## 6. 生成交付包

从源生成器创建全新目录，不覆盖旧目录：

```powershell
cd power-data-web
node scripts/build-gas-power-smoke-release.mjs `
  --release-id <不可变发布标识> `
  --unity-release-id <已归档且通过门禁的 Unity 构建标识> `
  --package-type <local-test|partner-integration|standalone-formal>
```

具体可选参数以当前脚本帮助和 `package.json` 为准。普通 `npm run build` 只验证前端，不能作为平台交付包。

最终目录至少包含：

- `scene-topology-manifest.json`；
- `release-manifest.json`；
- `unity/` 和 `unity/webgl-protocol-capabilities.json`；
- `shell/`、公共拓扑资源和完整性摘要；
- 与包类型匹配的自测/诊断边界。

门禁结果必须是 `valid` 且问题数为零。直接读取包内两份清单，复核动作、场景、第三层、节点映射、拓扑上下文和版本，不只相信源代码测试。

## 7. 平台交付清单

交给平台方：

1. 发布身份、包类型、目录路径和资源摘要。
2. 场景入口表：`sceneId`、默认 `topologyId`、资源版本、加载策略。
3. 公开动作表：`actionId`、目标场景、视图模式、拓扑/第三层、Unity 动作和失败策略。
4. 三层能力矩阵：外层协议、Unity 全局桥接、每个业务场景实际能力。
5. `nodeId` 节点绑定表和可选 `sceneNodeId`；不提供 `deviceId`。
6. 消息样例、错误码、状态取值和来源/端口说明。
7. 测试、类型检查、构建、生产审计和最终门禁结果。

## 8. 历史包警告

当前 `Builds/Releases` 中的历史包不能自动视为有效交付。交接时必须逐包执行 `validate-release-artifact`；若包内动作、第三层文件、清单或资源与当前审计不一致，应标为“历史无效包”，重新从源生成器构建，不能在旧目录上补文件。

## 9. 回滚

停止向新目录导流，恢复上一份完整且已通过门禁的目录；不要混用新旧前端、Unity 或清单。清理代理/浏览器中失败发布标识的缓存，重新验证握手、场景、拓扑、状态、第三层和释放。记录失败标识与根因，不能修改失败产物伪装为新版本。
