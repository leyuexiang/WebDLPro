# 模型节点、拓扑节点与沙盘标识规范

## 1. 应优先参考哪些文档

新增或改名时按下列顺序查阅：

1. [场景模型节点与拓扑节点命名规范](../前端原子任务/场景模型节点与拓扑节点命名规范.md)：模型对象、`nodeId`、`sceneNodeId`、`overviewBuildingId` 的主规则。
2. [场景拓扑动作映射规范](../前端原子任务/场景拓扑动作映射规范.md)：动作、第二层、第三层和双向引用规则。
3. [合作方节点绑定与状态对接确认结论](../前端原子任务/合作方设备绑定与状态对接确认结论.md)：平台内部设备号边界、状态快照和双方职责。
4. [新版数据交换格式拓扑图复刻制作规范](../前端原子任务/拓扑图/新版拓扑图复刻制作规范.md)：`penId`、拓扑文件、四态图元和拓扑切换。
5. [命名镜头定位接口接入说明](../前端原子任务/03-命名镜头定位接口接入说明.md)：`cameraPoseId` 与模型高亮目标的显式关联。
6. [通用拓扑图参考](../通用拓扑图参考0810_AI友好版.md)：只作为“图中标注设备—模型—工艺流程”业务语义参考；关键环节子表不能脱离总拓扑重新绑定，连接必须以已核验总表为准。
7. 当前代码：`types.ts`、`validator.ts`、`runtime-registry.ts`、Unity 场景控制器和发布门禁。代码与旧文档冲突时，以运行时和门禁共同证明的行为为准。

## 2. 四类标识的职责

| 标识 | 中文职责 | 唯一范围 | 是否进协议 |
| --- | --- | --- | --- |
| Unity 游戏对象名称（`GameObject`） | 编辑器可读名称 | 场景层级内可读 | 否 |
| 三维节点标识（`sceneNodeId`） | Unity 聚焦、状态、反向选择目标 | 同一 `sceneId` 内唯一 | 是 |
| 二维节点标识（`nodeId`） | 二维选择、状态快照和平台内部绑定主键 | 同一资源键内唯一 | 是 |
| 图元编号（`penId`） | 当前 JSON 文件中的视觉图元编号 | 当前文件内唯一 | 否，不跨文件使用 |
| 沙盘建筑标识（`overviewBuildingId`） | 总览建筑到目标场景入口 | 总览目录内唯一 | 仅内部场景入口 |
| 平台设备标识（`deviceId`） | 合作方真实设备主数据编号 | 平台内部 | 禁止进入我方 |

平台自己维护 `nodeId → deviceId`。我方清单、消息、缓存、拓扑 JSON 和三维反向选择都不接收或转发 `deviceId`。

## 3. 稳定标识格式

除平台设备号外，稳定标识满足：

```text
^[a-z][a-z0-9_]*(?:[.-][a-z0-9_]+)*$
```

长度 1—128、大小写敏感；优先小写字母、数字、点号和短横线。禁止中文、空格、路径、文件后缀、随机值、时间戳、坐标、`node1`、`temp`、`test`、`new`、`copy`、`unknown`。

## 4. 拓扑和二维节点

拓扑标识（第二层视图稳定标识，`topologyId`）：

```text
topology.<sceneId>.<view-purpose>
```

例如 `topology.gas-power.overview`。`view-purpose` 写稳定业务用途，不写“页面一”“新版”“大屏”。

二维节点标识（逻辑业务节点，`nodeId`）：

```text
<kind>.<business-role>[.<instance>]
```

类别包括：`asset`（设备/资产）、`system`（控制或信息系统）、`group`（汇总概念）、`endpoint`（边界端点）、`virtual`（无单一物理对象的逻辑节点）。与 Unity 成对的发电设备统一使用：

- 上层控制：`system.<technology>-<business-role>-control`。
- 下层现场设备：`asset.<technology>-<business-role>`。

节点移动、换图标、改标题或换坐标不改 `nodeId`；同一业务实体出现在多个拓扑时复用同一 `nodeId`。

## 5. Unity 模型对象和三维节点

Unity 包装对象建议使用 `<BusinessRole>_<Instance>`，如 `GasTurbine_1`、`GridOutput`；场景根使用 `SceneRoot`、`Environment`、`Equipment`、`Runtime`、`Effects`、`Cameras` 等职责名。导入模型的子对象、骨骼、动画、材质默认保留，避免破坏资源引用。

三维节点标识（Unity 对外逻辑目标，`sceneNodeId`）示例：

- 物理节点：`node.<technology>-<business-role>`。
- 控制聚合：`unit.<technology>-<business-role>.control`。
- 厂级聚合：`plant.<business-role>`。
- 确认的热点：`hotspot.<business-role>.<part>`。

`sceneNodeId` 不要求等于游戏对象名。一个三维节点可绑定多个目标；一个可点击对象只能有一个规范回传的 `sceneNodeId`。上层聚合可共享目标对象，但必须标记“只允许拓扑聚焦”，不得抢占下层反向选择。

## 6. 显式映射台账

每个场景提交以下表格，依据必须是正式业务资料、已核验模型或已确认拓扑：

| `topologyId` | `nodeId` | 中文标题 | `sceneNodeId` | Unity 目标 | 拓扑聚焦 | 三维反选 | 四态 | 依据 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `topology...` | `asset...` | 现场设备 | `node...` | 单一设备 | 是 | 是 | 是/否 | 正式资料 |
| `topology...` | `system...` | 控制系统 | `unit...control` | 设备+线+柜 | 是 | 否 | 否 | 正式资料 |

规则：一个 `nodeId` 最多一个 `sceneNodeId`；同一场景一个 `sceneNodeId` 最多反向对应一个 `nodeId`；没有三维依据就省略字段，不填空字符串。`unitySceneMappings.sceneNodeIds`、Unity 控制器、动作和拓扑节点必须使用同一批已登记值。

## 7. 沙盘建筑标识

`overviewBuildingId` 采用 `overview-building.<business-scene-id>`，必须与目标 `sceneId` 并列显式登记。一对一映射，不用于场景内设备聚焦、状态或流程。替换模型只改渲染器、碰撞体和必要资产引用，不改标识或切场景代码。

## 8. 改名和版本迁移

稳定标识发布后原则上不原地改名。若业务实体语义确实改变：

1. 建立“旧标识—新标识—原因—全部引用—确认人—验证日期”迁移表。
2. 同步更新 Unity 控制器、`unitySceneMappings`、基础拓扑、动作、第三层目录、测试夹具和清单。
3. 同一事务提升 `sceneMappingVersion`、`manifestVersion`、必要的资源和拓扑版本。
4. 通知平台按新 `nodeId` 刷新内部设备绑定；不要让平台把设备号回写我方。
5. 当前协议没有别名/重定向字段，不能只改一侧，也不能长期保留两个伪别名。

## 9. 命名验收清单

- [ ] `topologyId`、`nodeId`、`sceneNodeId` 格式、长度和唯一性通过校验。
- [ ] 标题、对象名、层级、坐标和图片没有被用作隐式映射。
- [ ] 映射节点均在 `unitySceneMappings` 和 Unity 控制器中登记。
- [ ] 可点击对象只有一个反向选择目标。
- [ ] 清单没有 `deviceId`、`deviceMappings` 或平台绑定数量字段。
- [ ] `penId` 仅属于当前拓扑文件，跨文件按显式 `penId → nodeId` 重新登记。
- [ ] 改名已同步所有反向引用、版本、测试和平台通知。

## 10. 自动校验重点

结构清单校验器会检查节点标识、标题、坐标、层级、状态、双击行为、显式 `sceneNodeId`、同场景反向唯一性、默认拓扑归属、动作双向收录和 Unity 映射注册。不要把这些规则只留在人工表格中；新增规则应进入 `validator.ts`、正向测试和负向门禁。
