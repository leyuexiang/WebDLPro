# 场景新增与沙盘绑定

## 1. 开始前：建立场景配置台账

在修改 Unity 或前端前，先填写：

| 字段 | 要求 |
| --- | --- |
| 用户可见名称 | 中文展示名，不作为稳定标识 |
| `sceneId` | 既有场景闭集中的稳定标识；新增闭集外场景属于架构变更 |
| `unitySceneKey` | Unity 场景目录中的稳定键 |
| Unity 场景路径 | `Assets/Scenes/Business/<Scene>.unity` |
| 默认 `topologyId` | 第二层默认拓扑；没有资料时明确“无” |
| `processId` | 没有第三层时明确“无” |
| 第二层关键环节步骤 | 标题、说明、顺序、`cameraPoseId`；没有命名镜头时明确“无” |
| 资源来源 | 模型、材质、纹理、拓扑 JSON、四态图片和业务资料 |
| 预期能力 | 外层协议、Unity 全局桥接、当前场景实际能力分层填写 |
| 未确认项 | 直接列出，并阻止对应能力发布 |

先查看 `git status --short`，把用户已有改动与本次范围分开。

## 2. Unity 场景配置顺序

### 2.1 目录、构建和身份

1. 在 `BusinessSceneCatalog.asset` 登记 `sceneId`、`unitySceneKey`、场景路径、可用性和声明能力。
2. 检查 `BusinessSceneBootstrapGenerator.cs` 生成的构建顺序：Bootstrap 第一、Overview 第二，其后是完整业务场景闭集。
3. 场景文件必须有独立稳定路径和元数据标识（全局唯一标识符，`GUID`）；不要删除重建以“换一个干净文件”。
4. 占位场景升级为真实场景时，先建立适配器和测试，再移除 `UnavailableBusinessSceneController`。
5. 若场景不在既有固定闭集，必须同时更新 Unity 闭集、前端闭集、校验器、测试和发布生成器；只新增 `.unity` 文件不算接入。

### 2.2 资源与骨架

模型、材质和纹理按场景归属，保留源模型和 `.meta` 文件。主模型与独立电线重叠时，只在场景实例停用重复渲染器，不删除源资源。复杂管网流动需要连续纹理坐标（`UV0`）或显式样条/中心线，不能指望着色器自动推断。

建议骨架：

```text
Main Camera
├─ Camera / AudioListener / UniversalAdditionalCameraData
SceneRoot
├─ Environment
├─ Equipment
└─ Effects
Runtime
├─ 场景控制器
├─ 相机控制器
├─ 命名镜头注册表（可选）
├─ 厂房入口控制器（可选）
├─ 第三层加载器、协调器、挂载点（可选）
└─ 测试或桥接组件
```

必须确认：只有一个活动音频监听器；主相机标签正确；相机初始变换是真实 `resetCamera` 基线；场景根、相机、上下文材质和运行时组件都用显式序列化引用。禁止用全场景查找、模糊名称匹配或扫描补映射。

### 2.3 三维节点、四态和选择

`PowerPlantProcessController._nodes` 每项至少登记稳定 `sceneNodeId`、目标对象引用、是否仅拓扑选中和可选焦点镜头。上层控制聚合节点可包含设备、控制线、控制柜，但必须标记 `_topologyOnlySelection = true`；下层现场设备通常只绑定一个主设备并允许反向选择。

四态登记在 `_visualStateBindings`：每个真实下层设备的正常、告警、故障、离线目标必须明确；一个渲染器只能属于一个状态节点，每个材质槽都要有控制器可写的颜色属性。未登记节点不是“离线”。只有全部四态目标有效时，才能声明更新/清除四态能力。

地面、空白和未映射对象点击必须清除选择并触发 `selectionCleared`。不要把普通二维连线自动解释为三维路径流；路径流能力必须有适配器实现和业务资料共同证明。

### 2.4 命名镜头和第二层按钮

Unity 的 `BusinessSceneNamedCameraPoseRegistry._cameraPoses` 每项登记稳定 `cameraPoseId`、目标变换和高亮目标。前端只发送 `moveCameraToPose({ cameraPoseId })`，不发送坐标、旋转或 Unity 路径。

前端在 `camera-pose-navigation.ts` 为场景加入闭集和独立只读按钮数组；按钮顺序就是界面编号。说明只表达已确认的输入、处理和输出。场景未登记命名镜头时返回空数组，不借用其他场景步骤。

按钮只负责镜头与说明，不改变二维选择、流程、四态或第三层。进入第三层、场景切换、相机复位后清除活动按钮、在途状态和说明气泡。高亮、淡化和透明必须是运行时临时效果，退出步骤、复位、切场景和释放时恢复原材质；禁止创建持久“步骤专用材质”。

### 2.5 第三层关键环节

只有存在独立精细资源才登记。流程如下：

1. 创建包装预制体（`Prefab`），源模型作为嵌套预制体保留。
2. 配置第三层相机、动态控制器和四态目标。
3. 在 `ProcessDetailCatalog.asset` 登记 `processDetailId`、`sceneId`、`processId`、`stepId`、`resourceId`、`cameraPoseId`、`stateNodeId`。
4. 场景装配第三层资源加载器、协调器和挂载点，并绑定二层根、控制器和相机。
5. 前端同步 `processDetails`、`enterProcessDetail` 动作和独立 `topologyDataContextId`。
6. 第三层动作只能用 `targetViewMode: process-detail` 和 `processDetailId`，不能带第二层 `topologyId`。

没有独立资源时不创建空动作、假目录或占位能力。

## 3. 沙盘场景如何绑定

沙盘代表建筑标识（总览建筑稳定标识，`overviewBuildingId`）使用：

```text
overview-building.<business-scene-id>
```

每栋建筑必须显式并列登记唯一 `overviewBuildingId` 和目标 `sceneId`，禁止从字符串、对象名称、层级路径或数组序号推导。它不是业务场景的 `sceneNodeId`，不能用于聚焦、显隐、流程或设备状态。

绑定步骤：

1. 在总览目录为建筑登记 `overviewBuildingId → sceneId`。
2. 在 Unity 场景中给代表建筑绑定渲染器（`Renderer`）、碰撞体（`Collider`）和必要视觉引用。
3. 点击入口由总览控制器按显式映射发起 `switchScene`/受控总览动作；不要把建筑名称直接当场景键。
4. 替换建筑模型时只重新绑定渲染器、碰撞体和资产，不改场景切换代码，也不改变两项稳定标识。
5. 对已具备正式 Unity 资料的总览目标，`overviewBuildingId → sceneId` 必须一对一；换流站保持无设备三维映射，开关站已完成 4 个语义节点和 2 组设备状态目标配置，但二维拓扑逐图元映射仍需显式补充。

沙盘建筑、场景节点、拓扑节点是三套不同概念：建筑负责“进入哪个场景”，`sceneNodeId` 负责“场景内聚焦哪个三维目标”，`nodeId` 负责“二维业务与平台状态关联哪个逻辑节点”。

## 4. 三层能力核对

| 层级 | 事实源 | 结论 |
| --- | --- | --- |
| 外层平台协议 | `HOST_COMMAND_TYPES`、`HOST_EVENT_TYPES` | 当前构建对外能收发什么 |
| Unity 全局桥接 | `WebGlProtocolContract`、`unity/webgl-protocol-capabilities.json` | 播放器能识别什么 |
| 当前业务场景 | `DeclaredCapabilities`、适配器 `Capabilities`、场景序列化 | 该场景真实能执行什么 |

例如全局桥接可识别 `setRouteFlow`，不等于燃气或燃煤适配器支持路径流；平台能力表必须按场景写“支持/不支持/条件支持”。

## 5. 场景完成定义

Unity 场景、目录能力、拓扑、动作、二维—三维映射、版本、测试、发布摘要和平台交付说明全部同步，且目录能力与运行时能力完全一致，才可标记场景完成。
